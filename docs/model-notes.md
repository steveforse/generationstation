# Model notes

Measurements, set-up facts and decisions for each model and worker. They are kept because the numbers are still true and the choices explain the catalog. What the app does is in `docs/context.md`; setting a machine up is in `docs/setup-macos.md` and `docs/development.md`. Each entry says where it was measured; dates are when. Weights, licences and scores for every model are also in the runtimes catalog (`runtimes.example.json`, `runtimes.mac.example.json`).

### Thinking levels

- The owner asked for the models' own thinking levels instead of an on/off button, showing only values the model takes. The engines report only whether a model takes an effort, not which names, so each card setup lists its levels in the runtimes file (`thinking_levels` lowest first, `thinking_default`, `thinking_off`); the catalog gives the chat the levels of the model's latest launch, the composer offers exactly those (plus Off where a request can turn thinking off) and remembers the choice per model on the device, and the host refuses a level the running model does not take (`THINKING_LEVEL_INVALID`). A card without levels keeps plain on/off. The help assistant still asks for off.

- Levels, from each engine's code: Inkling 2 Mini (its template, on Basalt 0.5.5 and Strata) none/minimal/low/medium/high/xhigh/max as 0 to 0.99, where xhigh and max are both 0.99, so the chat offers minimal, low, medium, high and max; DeepSeek V4.1 Flash (Basalt) low, high, max (medium is high); Qwen3.8 Flash-Next (Basalt's `qwen4exp` template) low, medium, xhigh (high and max become xhigh). Defaults: Inkling high on the 5090, low on the 4080 (the help assistant's card), DeepSeek high, Flash-Next xhigh.

- Strata 0.2.19's Inkling module treated the model as having no thinking mode: it rewrote every request to effort "none" and dropped the thinking channel, although the model still thinks at "none" (6-9K characters on a hard counting question, unseen while the person waited). `workers/strata_inkling_thinking.py` starts Strata's server with those three spots changed in memory (Strata's files stay untouched; it refuses to start if they are gone after an update), turned on per card with `inkling_thinking`. Measured on the 4080, 2026-11-23: thinking grew with the level (about 5.7K characters at low, 12.5K at high, 22K at max on that question, 115-130 tok/s throughout); through the app each level reached the model and its thinking showed, and the answers (sampled at temperature 1.0) were mostly right with an occasional miss at low.

### Qwen Image 2.1 worker

Measured 2026-11-14/15 on the desktop, 1024x1024, outside the API (benchmark scripts, then the worker started exactly as the plugin launches it and driven over the worker protocol). The API-managed run is recorded below.

- Files under `D:\ai\models\qwen-image-2.1\`: `uncensored\` (ChatR Labs Uncensored Omni: Qwen-Image-2.1 with their rank-128 adapter merged; NVFP4 ComfyUI file and other builds), `turbo-quant\` (official Qwen-Image-2.1-Turbo, NVFP4 and FP8), `turbo\` (Turbo's Diffusers folder: text encoder Qwen3-VL 8B, VAE, processor, scheduler), `base\` (Qwen-Image-2.1 scheduler and configs), `lightning\` (4-step Lightning adapter, used for "quick").
- Worker environment `C:\ai\envs\qwen-image-worker`: torch 2.14.1+cu130, diffusers 0.43.0, transformers 5.22.2, torchao 0.18.0, peft 0.21.2, torchvision 0.29.1, triton-windows 3.9.0.post30 (needed for compiling; without it the worker runs uncompiled and NVFP4 is slower than FP8). The environment has no pip; install with `uv pip install --python <env python>`.
- NVFP4 on the RTX 5090 runs real 4-bit maths (torchao, Blackwell only). The RTX 4080 has no 4-bit maths: the worker keeps the weights in 4 bits on the card and expands each layer to FP8 just before its matmul (checked against torchao's decoder: 0.1% difference, BF16 rounding).
- Each transformer block is compiled (Diffusers regional compilation). The first picture at each quality and shape after a start is slower; compiled kernels are cached on disk, so later starts warm up faster (5090: 21 s first time, 9 s later). Diffusers' prompt KV cache is off: with compiling it recompiled for every prompt length and saved nothing measurable.
- The text encoder stays in system RAM in BF16 and runs on the processor: 0.4-0.6 s per prompt. Swapping parts between RAM and the card was slower, and keeping the encoder on the 4080 next to the transformer overflowed it: Windows then backs PyTorch's cached memory with system RAM and each step took 40-120 s instead of about 1 s.
- Times per picture after warm-up, through the worker: RTX 5090 uncensored quick 1.7 s, best (35 steps, CFG 5) 15.2 s; RTX 4080 uncensored quick 3.6 s, best 42.3 s, Turbo (8 steps) 5.5 s. Earlier benchmark, 5090 Turbo NVFP4 1.9 s. For comparison, the 4080 with FP8 weights swapped per picture took 7.8 s / 45.8 s / 10.7 s.
- Card memory: peak 12.9 GiB reserved on the 5090 and 12.5-12.6 GiB on the 4080 (plus the CUDA context); between pictures the worker returns its cache, leaving about 5-5.6 GiB in use. Estimates: 15 GiB free on the 5090, 14 GiB on the 4080, 28 GiB RAM (measured 25.6 GiB committed, 18.6 GiB peak working set, with the prompt reader on the CPU).
- First run through the API, 2026-11-15, RTX 5090, Uncensored preset: start, three pictures (quick square 2.2 s, quick portrait 2.1 s, best square 19.6 s including its first-time preparation) fetched as PNGs, then stop. Stop freed the card to 0 MiB.
- NVFP4 small lettering at best quality is weaker than FP8's. Community INT4 (SVDQuant/Nunchaku) builds exist only for the stock model, need a Nunchaku fork with Linux wheels, and official Nunchaku does not support 2.1 yet (checked 2026-11-15).

### MiniMax H3 pictures and picture edits

- MiniMax H3 (shown as "MiniMax H3 videos & pictures": one runtime, so a running H3 switches between clips and pictures without reloading) has two picture tabs beside its video tabs: "A picture" (text to picture) and "Edit pictures" (up to 4 pictures and what to make with them, on H3's reference transformer). It uses the community one-frame method (ComfyUI-Fizgig-H3-Still, H3 Image Studio) on the existing NVFP4 video transformer, with nothing new downloaded: the layout is resolved for one latent frame (the worker patches Diffusers' latent frame count and 5 s minimum only while making a picture), and because one latent frame decoded alone comes out banded, it is repeated to one decoder chunk and the fourth frame after the decoder's padding kept. The separate MiniMax-H3-Image checkpoint (about 66 GB transformer plus H3's 66 GB text encoder, its own licence) was not used.
- Sizes 1, 2, 4 and 8 MP (picture edge rounding is not capped at 1344 like clip frames); quality Standard, High (default) or Extreme. The Turbo add-on is left out: at full strength it smears pictures. Direct worker runs on the RTX 5090 (no speed-up): 2 MP High 21 s, 4 MP Standard 38 s, 4 MP High 63 s, 8 MP High 120 s, peak 25.6 GiB; an edit at 2 MP High 88 s including the switch to the reference transformer. Through the app (speed-up on): 4 MP Standard in 26–30 s. In an edit (storm to sunny day) H3 kept the lighthouse, buildings, rocks and composition and changed only weather and light.
- Modes can declare their own output kind (`ModeSpec.output_kind`); the page labels the button per tab ("Make a picture") and says "Your results" when a model makes more than one kind. Picture workers (H3 pictures, Qwen Image) save 1024 px thumbnails, and the chat model is shown the thumbnail instead of a picture over 1.2 MP (read from the PNG header): a full 4 MP picture took Inkling minutes to read on the RTX 4080, the thumbnail 15 s.

## Video: MiniMax H3

Measured 2026-11-15 to 2026-11-21 on the RTX 5090, 960x544, 124 frames (5.2 s at 24 fps) with sound.

- Files under `D:\ai\models\minimax-h3\`: `diffusers\` (MiniMaxAI/MiniMax-H3 configs, tokenizer, schedulers, video and audio decoders), `nvfp4\minimax_h3_fl2va_pruned_nvfp4.safetensors` (11.7 GiB, ComfyUI NVFP4 "pruned" transformer), `uncensored\heretic-bf16\` (llmfan46's abliterated Qwen3-VL-32B-Instruct, BF16), `turbo-v4\` (larryvrh Turbo v4 step-600 EMA add-on and the `h3_silu_temb_grid` it needs), `comfy\loras\` (Comfy-Org Turbo v1.0, unused). Environment `C:\ai\envs\minimax-h3-worker`: the Qwen Image environment's pins plus PyAV 19.0.2 and psutil.
- The pruned checkpoint replaces H3's timestep embedder with a 1025x8 table and has ComfyUI tensor names; Diffusers 0.43's converter refuses it, so the worker maps names, splits fused q/k/v, swaps the feed-forward halves, and projects the table row without SiLU. MiniMax's own text encoder is byte-identical to stock Qwen3-VL-32B; H3 reads the un-normed hidden state after decoder layer 50, so only 50 layers are loaded (BF16, on the processor, about 2 s per prompt). An uncensored NVFP4 encoder from another uploader decoded to garbage and was deleted.
- Build comparison (2026-11-16, page "MiniMax H3 Build Test"): NVFP4 and ComfyUI FP8 looked equivalent; FP8 did not fit on the card with a Turbo add-on unless the video decoder streamed from RAM, and was 12% slower per step. Turbo v4 looked crisper than Comfy-Org's v1.0. NVFP4 + Turbo v4 was chosen; the FP8 file was deleted.
- H3 is trained on a structured prompt (`integrated_multimodal_description: [Shot 1] ...`, `overall_soundscape:`, `non_diegetic_music:`; spoken lines as `(S1) says: <d>[English] ...</d>`). The worker builds it from the form's description, sounds, music and look, turns `says: "..."` into a spoken line (one speaker), and passes a prompt that already starts with the structure through unchanged.
- First API-managed run, 2026-11-21: ready in 43 s (worker 22 s); quick (Turbo v4, 4 steps) 5 s clips 38-39 s after a 92 s first clip that compiles; best (20 steps) 164 s including its first compile (about 143 s warm in the comparison). Peak 24.4-24.6 GiB reserved; between clips about 20.5 GiB stays in use (transformer and decoders). The worker's peak working set was 51-54 GiB and its committed memory 87-89 GiB (Windows also counts the card's allocations there). Stop freed the 5090 to 10 MiB.
- A 10 s clip (243 frames) worked but took 135 s at quick and peaked at 29.7 GiB, above the 29.4 GiB admission allows on the 5090 after headroom, so the plugin first offered 5 s only. Since 2026-11-22 large clips (over 100 million frame pixels) let the video decoder and the transformer take turns on the card (each waits in system RAM while the other works, one to two seconds per move), and Length offers 5, 10 and 14.4 s (345 frames, the most H3 accepts below its 360-frame limit): 10 s up to 540p (and the AI upscale, which renders 540p), 14.4 s up to 480p. Through the app at Low (Fast): 10 s 480p in 96 s (23.0 GiB peak), 10 s 540p in 130 s (25.2 GiB), 14.4 s 480p in 162 s (26.7 GiB); 5 s 720p now peaks at 24.5 GiB. Worker RAM peaked at 66 GB. The pipeline otherwise takes its working device from the transformer, so the video pipelines (not the CPU prompt readers, which share their class) are pinned to the card. Estimates: 28 GiB free on the 5090 (the 4080 is not allowed), 60 GiB RAM.

### Upscaling to 1080p

- The H3 latent upscaler (LBH-123-AI) is not offered: upscaling alone looked worse than a Lanczos resize, and refining at 1088x1920 does not fit the RTX 5090.
- Moving the NVFP4 transformer between the card and system RAM takes about 1.7 s each way; with it in RAM, decoding at 1088p peaks at 18.3 GiB instead of 32.9 GiB.
- FlashVSR+ (OpenImagingLab, Apache 2.0; turbo and base weights in `D:\ai\models\flashvsr-plus`, reached through a junction from `C:\ai\tools\FlashVSR_Plus\ckpts`): environment `C:\ai\envs\flashvsr-worker` (torch 2.14.1+cu130, triton-windows, FlashVSR+ and its Triton block-sparse attention kernel; the SDPA fallback refuses sequences this long, and Python needs UTF-8 mode on Windows). 540p to 2048x1152 on the RTX 5090: turbo 35-40 s at 13 GB, base 40-45 s at 20 GB, including loading; clearly more detail than a Lanczos resize (stitching, rivets, background), turbo and base close.
- H3's resolution "1080p (AI upscale)" renders 540p, parks the transformer in system RAM, runs FlashVSR+ base as a separate process on the same card (sides divisible by 128, proportions kept), crops and scales to the exact final size. Through the app: 106 s for a 5 s clip (FlashVSR+ about 48 s); worker RAM peaked at 62 GB, so H3's RAM estimate is 72 GiB. "1080p (fast resize)" (720p resized) remains. The latent upscaler is not offered.

### Drama 3

- Chosen for expressive speech: directions written into the text in square brackets ([whispers], [laughs], [sighs], [angry], [nervous]...). Fish Audio S2 Pro was the alternative; the owner chose Drama 3 (35B MoE, 3B active, October 2026, Fish Audio Community Licence: non-commercial and small-business use). Shown as "Drama 3 speech" (`fish_drama3` plugin, port 8220).

- The Windows worker (stdlib only, run with the backend's Python) writes a bash wrapper into its launch folder and runs it with `wsl.exe`: it stops any server left from an earlier start (PID file), checks the model folder is visible (D: must be mounted in WSL), starts `sgl-omni serve` in its own process group with the environment on PATH (ninja builds kernels), and stops it when the worker's heartbeat file (touched every 3 s) is older than 20 s, since the app stops workers by terminating them. Stopping through the app freed the 5090 within 2 s with no processes left in WSL.
- Windows charges WSL's GPU memory to the VM process `vmwp`; plugins may name such helper processes (`gpu_helpers`), whose GPU memory then counts for the running model (display only), so the memory graph shows Drama 3 instead of "Other programs".
- Multi-voice scenes are performed natively in one pass per passage, with Drama 3's `<|speaker:N|>` tags, as Fish Audio's own `build_drama3_prompt` does. Upstream SGLang-Omni refuses every speaker but 0 (it dropped the multi-speaker path when Drama 3 was added, although its prompt builder already keeps a reference's own speaker tag); `workers/patches/sglang-omni-drama3-multispeaker.patch` removes that refusal and the worker applies it at start when the checkout lacks it.
- Sampling is Fish's reference sampling (`--tts_engine.factory.reference_sampling true`) with Fish's recommended temperature 1.0, top-p 1.0, epsilon 1e-3. Measured on the same three scenes (2026-11-23): with SGLang's default samplers about half of multi-speaker takes fell silent after the first line (three-voice scenes 1 in 4 complete); Fish's 0.7/0.7 with top-k 30 was worse; with reference sampling 21 of 24 takes were complete.
- Every take is checked and made again (up to 3 times; else the best is kept) when it ran to the 512-frame limit (about 23.8 s, the model fell silent), has less than 0.62 of the speech its letters need at 13 letters/s (on 31 takes with known outcomes every complete take was at 0.68 or more), or, with the speech-to-text check, holds less than 80% of its words. The check is `workers/asr_check.py`, a small Whisper (`D:\ai\models\whisper-base.en`) kept running on the CPU in OmniVoice's environment: about 1 s per 15 s of speech (Whisper large-v3-turbo took 3.7 s). Silences over 1.2 s are shortened to 0.7 s and trailing silence trimmed.
- Text is split into passages of at most 200 UTF-8 bytes and three speakers, cut at sentence ends (Fish's own code uses 300 bytes with a 1024-frame limit; with 512 frames, 300-byte narration ran into the limit). Each character gets a reference voice: their sample, or (when a scene or text needs several passages) a short take of their opening (at most 120 bytes; references are limited to 15 s) in a voice the model picks, so voices stay the same across passages. Characters without samples can come out with similar voices; samples avoid that.
- Final run through the app (2026-11-23), all complete by Whisper transcript: a 57 s reading in a model-picked voice (4 passages, 16.7 s), the same reading in a cloned voice (42 s, 11.5 s), a two-character scene with both voices cloned (3.1 s), three takes of a three-character scene (3-7 s, one take redone), and an eight-line four-character scene in three passages (27 s, 13.5 s, one take redone). Earlier runs: a cloned single voice; a two-character scene with both voices cloned; a three-character scene; an eight-line four-character scene (27.9 s in 6.2 s, three passages, no retries). Whisper transcripts had every line, and per-sentence pitch showed distinct, consistent characters (the Captain 131-147 Hz in different passages). No seed is accepted by SGLang-Omni, so takes cannot be repeated exactly (llama.cpp's Drama 3 support, Q4_K_M 20.6 GB GGUF, takes seeds and speaker tags natively but its voice cloning is undocumented for Drama 3; it was not needed). The NVFP4 community build (Reza2kn/drama-3-nvfp4) loaded in SGLang-Omni but its engine needs 25.9 GB, so the preprocessing stage had to move to the CPU, and its NVFP4 experts then failed in Drama 3's logits path with FlashInfer CUTLASS (TRT-LLM expected a missing `g1_scale_c`); it was set aside since it offered no multi-speaker or cloning gain.

Frame grabs for name reading: 0.31 s as PNG, 0.16 s as BMP, VideoToolbox 1.7 s per single-frame seek (startup cost), so BMP, four ffmpeg processes ahead of the OCR. Speech recognition already runs on the GPU (MLX).

- Editing the notes, 2026-11-26: `PUT /api/jobs/{id}/notes` {revision, summary [str], actions [{task, owner?, due?, time?}], decisions [{decision, by?, time?}]}; each list sent replaces the saved one and a list left out is untouched. It shares the transcript edit's `revision` guard (409 on a stale one) and lock, rewrites `meeting.json`, `notes.md`, `actions.csv` and `decisions.csv` (through `render_notes` in `workers/meeting_transcript.py`, which the worker now uses too), and keeps the notes as first written once under `notes_original`. Every saved edit, to the notes or the transcript, adds an entry to `history` in `meeting.json` ({revision, at, changes [{section, kind added/removed/changed/renamed, before, after, detail?}]}, newest last, at most 200 entries); the UI shows it as "Change history" under the transcript, newest first. There is no author on an entry because the app has one shared token. A transcript edit still leaves `notes.md` as written.

- Editing a transcript, 2026-11-26: `PUT /api/jobs/{id}/transcript` {revision, rename {label: new}, segments [{index, speaker?, text?}]} on a finished meeting rewrites `meeting.json` (revision +1, `edited`) and `transcript.md/.srt/.vtt` through the worker's own renderer (`meeting_transcript.render`); the notes and `transcript-raw.json` are not touched, so the notes can still name a speaker the person has since renamed. A stale revision gets 409, a bad index or an empty segment 422. The result view has an Edit transcript mode: a panel to rename a speaker everywhere, and per segment a speaker field (with the current names) and the words. A speaker renamed on all of their segments to a name nobody has yet is sent as one rename; anything else per segment.

- Not built: naming speakers in a form the person confirms before the notes (the model still proposes names on its own), one file per participant, and the VibeVoice and Nemotron engines on a Mac.
